LinguaMind Cognitive-Aware AI Reading Assistant

不是让 AI 替用户读，而是让 AI 根据人的语言认知特点辅助理解——按认知负荷动态调节解释深度。

产品设计文档 · V1 · 2026-09-28 · 语言智能 × 认知负荷理论
01 · 定位

它跟普通翻译器 / 总结器有什么不同

普通工具回答"这句话什么意思"；LinguaMind 回答"这句话对这个读者来说有多难，以及怎么讲他才能懂"。

  • 普通工具：把英文翻成中文，或给出摘要。读者能不能消化，工具不关心。
  • LinguaMind：先分析文本的句法复杂度、词汇难度、信息密度，评估读者当下的认知负荷，再决定用简化模式（先看懂大意）还是深度模式（句法树、术语、学术背景）。

一句话：它模拟的是"一位懂语言学的老师怎么给你讲"，而不是"一台翻译机怎么给你翻"。

MODE · SIMPLE

简化模式

先讲清楚"这段话在说什么"。句子被拆成主干，生僻词用大白话解释。适合高认知负荷时快速抓大意。

MODE · DEEP

深度模式

提供句法树、关键词解释、学术背景。适合低负荷 + 想精读时，逐层拆解。

OUTPUT
用户界面输出
复杂度评分 + 双模式解释 + 模式一键切换 + 反馈埋点
03 · 模式对比

简化模式 vs 深度模式

同一个句子，按读者的认知负荷呈现两种讲解深度。

原句：The interaction between semantic interference and syntactic complexity places a heavy burden on the reader's working memory.

维度简化模式深度模式
一句话大意两种困难同时出现时，大脑理解会更吃力。语义干扰与句法复杂度相互作用，占用读者工作记忆资源。
句法只保留主干，拆掉嵌套。给出句法树，标出嵌套定语从句位置。
术语"semantic interference" 用大白话解释。保留术语，附学术定义与背景。
适用认知负荷高，先抓大意。认知负荷低，想精读。
04 · 数据结构

接口定义（JSON Schema 级）

这三份结构可直接被后端复用——设计阶段先把数据定稳，后面写代码不返工。

① 输入 Request
{
  "text": "The interaction between semantic interference and
          syntactic complexity places a heavy burden on working memory.",
  "user_level": "graduate",      // undergrad | graduate | researcher
  "mode": "deep"                 // simple | deep（可让系统自动建议）
}
用户等级 + 期望模式驱动"认知负荷评估"的权重与讲解深度。
② 语言分析模块中间产物（核心差异化数据）
{
  "sentence_analysis": {
    "token_count": 18,
    "sentence_length": 18,
    "dependency_depth": 5,          // 依存树最大深度
    "structure": "nested relative clause",
    "has_long_clause": true
  },
  "vocabulary": {
    "difficult_words": [
      { "word": "semantic interference", "cefr": "C1", "is_academic": true },
      { "word": "syntactic complexity",  "cefr": "C1", "is_academic": true }
    ],
    "academic_word_ratio": 0.35
  },
  "info_density": {
    "noun_count": 6,
    "technical_terms": 2,
    "named_entities": 1
  },
  "complexity_score": 8.5,          // 0-10，认知负荷打分
  "cognitive_load_level": "high"    // low | medium | high
}
这一份就是你的"护城河数据"——面试时讲清楚这些字段怎么算出来、为什么重要。
③ 输出 Response
{
  "complexity_score": 8.5,
  "cognitive_load_level": "high",
  "difficult_words": ["semantic interference"],
  "sentence_analysis": {
    "structure": "nested relative clause",
    "difficulty_reason": "high syntactic load"
  },
  "explanation": {
    "simple":  "两种困难同时出现时，大脑理解会更吃力。",
    "academic": "语义干扰与句法复杂度相互作用，共同占用读者工作记忆……"
  },
  "recommend_mode": "deep"
}
explanation 由 LLM 根据②的结构化分析生成；②是证据，③是结论，二者分离、可追溯。
05 · 精简 PRD

MVP 范围与评价指标

先把最小可证明价值的版本定下来，指标从第一版就埋点。

用户画像

核心用户：非英语母语的本科生 / 研究生，正在读英文论文，卡在长难句与专业术语。

次要用户：科研人员、备考（雅思 / 考研英语）人群。

痛点：翻译器给出结果却读不懂，总结器跳过细节却丢了论证。

MVP 功能
  • 文本粘贴 / PDF 上传
  • 四个维度的语言分析（句法、词汇、信息密度、长难句）
  • 复杂度评分 + 负荷分级
  • 简化 / 深度双模式解释，一键切换
  • 用户等级选择（本科生 / 研究生 / 科研）
评价指标
(埋点)
  • 简化模式下，读者自评"是否看懂"的正确率（理解反馈按钮）
  • 模式切换频率——高负荷文本是否更倾向切到简化
  • 每次解释的"有帮助 / 没帮助"点赞点踩
  • 平均阅读时长（相比纯翻译器是否更高效）

这些指标让你从"功能 demo"升级为"研究型产品"——回答面试官的"你的创新凭什么成立"。

差异化护城河

不是"会用 API"，而是把语言学研究问题（人类处理复杂句的认知限制）转化成产品能力——认知负荷评估这一层是别人抄不走的。
